# Internationalization (i18n)

The UI supports German and English via
[`i18next`](https://www.i18next.com/)/[`react-i18next`](https://react.i18next.com/).
This doc covers how it's wired up and the rules to follow when adding
or changing translated strings. For the app's other conventions see
`AGENTS.md`.

## How it's wired up

- `frontend/src/i18n/index.ts` initializes `i18next` with a single
  `translation` namespace per language, loaded from
  `frontend/src/i18n/locales/de.json` and `en.json`.
- `fallbackLng: "de"` and `supportedLngs: ["de", "en"]` — any other
  browser locale falls back to German.
- `i18next-browser-languagedetector` picks the initial language from
  `localStorage` first, then the browser's `navigator` language, and
  persists the user's choice back to `localStorage` on change (see
  `detection.order`/`caches` in `index.ts`).
- The language switch itself lives in `frontend/src/components/Sidebar.tsx`
  (the DE/EN buttons at the bottom of the sidebar) and calls
  `i18n.changeLanguage("de" | "en")` directly — there's no routing or
  URL-based locale, it's a single global `i18n.language` value that
  every component reads via `useTranslation()`.

## Adding or changing a string

1. Add the key to **both** `locales/de.json` and `locales/en.json` —
   never leave one language file ahead of the other. The two files
   must have exactly the same set of keys at all times.
2. Use `t("namespace.key")` in the component
   (`const { t } = useTranslation();`). Never hardcode new UI copy
   (buttons, labels, page text, confirm dialogs, error messages)
   directly in a component.
3. Keep keys nested by feature/page (see the existing top-level groups
   in `de.json`: `common`, `fields`, `nav`, `dashboard`,
   `invoices`, `expenses`, `settings`, …). Add a new top-level group
   for a new page rather than dumping unrelated keys into `common`.
4. Interpolation uses the standard i18next `{{variable}}` syntax in the
   string value and a second argument to `t()`:
   `t("invoices.deleteConfirm", { number: invoice.number })`.
5. Keep the German tone direct and slightly informal ("du"), matching
   the existing strings — this is a single-user home tool, not
   corporate software.

There is currently no automated check that `de.json` and `en.json`
have matching keys (a missing key just falls back to the fallback
language's key path being rendered instead of the fallback text, which
is a silent-ish failure) — visually check both files in the diff when
you touch either one.

## The exception: the printable invoice document

The `.invoice-doc` block rendered in
`frontend/src/pages/InvoiceDetail.tsx` — the actual invoice a client
receives — is **hardcoded German and does not go through `t()`**. This
is intentional and must not change: it's a legally binding document
under German tax law (Kleinunternehmerregelung §19 UStG), and its
language must not follow the logged-in user's UI language preference.
Everything *around* the document itself (the page's buttons, the
"back" link, confirm dialogs) is translated normally through `t()` —
only the invoice content block itself is exempt.

If you're adding new content to the invoice document, write it in
German directly; don't add an i18n key for it.

## Locale-aware formatting

`frontend/src/utils.ts` exports two helpers that take an explicit
`lang: "de" | "en"` parameter (the `Lang` type from `types.ts`) rather
than reading `i18n.language` internally, so callers can force German
for the invoice document regardless of the current UI language:

- `fmtEUR(amount, lang)` — currency formatting via `Intl.NumberFormat`.
  Note German and English locales format currency differently (decimal
  separator, and the space before "€" is a non-breaking space,
  `U+00A0`/`U+202F` depending on locale — don't compare formatted
  output against a string with a plain space in tests).
- `fmtDate(isoDate, lang)` — date formatting via
  `toLocaleDateString`.

Pass `i18n.language` (normalized to `"de"`/`"en"`, see the
`lang = i18n.language?.startsWith("en") ? "en" : "de"` pattern in
`Sidebar.tsx`) from UI components, or the literal `"de"` when
formatting content that belongs to the invoice document.

## Stored values vs. displayed labels

`EXPENSE_CATEGORIES` in `utils.ts` are canonical English-ish keys
(`"equipment"`, `"software"`, …) stored as-is in the database and never
translated. Only the *label* shown to the user goes through
`t(\`expenses.categories.${category}\`)` — add a translation for a new
category under `expenses.categories` in both locale files, but never
change or translate the stored key itself (that would silently break
existing expense rows that already reference the old key).

## Testing translations manually

Run the frontend dev server (`npm run dev` in `frontend/`) and use the
DE/EN switcher in the sidebar to click through every page in both
languages, checking for:

- Untranslated strings (a raw key like `invoices.deleteConfirm`
  rendering literally means the key is missing from that language's
  JSON file).
- Text overflow/wrapping — German strings are often meaningfully
  longer than their English equivalent for the same UI element.
- The invoice document itself staying German regardless of which
  language the switcher is set to.

There is no automated visual/snapshot test for translated UI text;
`frontend/src/App.slow.test.tsx` covers app-level behavior, not
translation coverage.
